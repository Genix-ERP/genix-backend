# Backend Spec — Catalog Search & Ordering

> **Audience:** backend team (Django REST Framework, `api.pattapay.uz`).
> **Author:** mobile team. **Status:** requested — not yet implemented.
> **Verified:** all "current behavior" claims below were reproduced with live
> `curl` against `https://api.pattapay.uz` on 2026-06-25.

## Problem

The mobile clients (and web) send free-text **search** and **sort/ordering**
query params to two catalog list endpoints, but the backend silently ignores
them — it returns `HTTP 200` with the **full, unsorted** list. Users type a
query and get unrelated results, or pick a sort and nothing changes.

The category/specialization/region/price/experience **filters already work** —
this spec only covers the two missing capabilities: `search` and `ordering`.

| Endpoint | `?search=` | `?ordering=` | Working filters (no change) |
|---|---|---|---|
| `GET /api/lawyers/` | ❌ ignored | ❌ ignored | `specialization`, `region`, `min_rating`, `max_rate`, `min_experience` |
| `GET /api/documents/templates/` | ❌ ignored | ❌ ignored | `category`, `kind`, `is_featured`, `min_price`, `max_price` |

Root cause: these `ViewSet`s are missing `filters.SearchFilter` /
`filters.OrderingFilter` in `filter_backends` (and the matching
`search_fields` / `ordering_fields`).

---

## 1. `GET /api/lawyers/`

### Current behavior (reproduced)
```
GET /api/lawyers/?search=soliyev            → count=3 (full list, unfiltered)
GET /api/lawyers/?q=soliyev                  → count=3
GET /api/lawyers/?name=soliyev               → count=3
GET /api/lawyers/?ordering=-rating           → identical order to default
GET /api/lawyers/?ordering=consultation_rate → identical order to default
GET /api/lawyers/?ordering=-experience_years → identical order to default
```
(Proof that ordering is dead: a lawyer with `rating=5.00` is returned **last**
under `ordering=-rating`.)

### Required behavior
- `?search=<text>` — case-insensitive **partial** match (`icontains`) across the
  lawyer's name and headline.
- `?ordering=<fields>` — DRF comma-separated multi-field ordering. Must accept
  every field the clients send (see "Client contract" below).

### Serializer fields available (for reference)
`user_id, full_name, headline, specialization, experience_years, region,
consultation_rate, rating, reviews_count, answers_count, consultations_count,
available_slots_count, is_verified, preferred_language, avatar`

### Implementation (DRF)
```python
from rest_framework import filters

class LawyerViewSet(...):
    filter_backends = [
        DjangoFilterBackend,          # keep — existing filters
        filters.SearchFilter,         # ADD
        filters.OrderingFilter,       # ADD
    ]

    # NOTE: search_fields are MODEL fields, not serializer fields.
    # `full_name` is almost certainly derived from the related User —
    # map to the real columns (adjust to your schema):
    search_fields = [
        "user__first_name",
        "user__last_name",
        "headline",
        "specialization",
    ]

    ordering_fields = [
        "rating",
        "reviews_count",
        "experience_years",
        "consultation_rate",
    ]
    ordering = ["-rating", "-reviews_count"]   # default when no ?ordering=
```

### Client contract — exact `ordering` values the apps send
The mobile sort menu maps 1:1 to these strings; all referenced columns **must**
be in `ordering_fields` or DRF drops the unknown field silently:
| Sort option | `ordering=` value |
|---|---|
| Top rated (default) | `-rating,-reviews_count` |
| Most reviewed | `-reviews_count,-rating` |
| Most experienced | `-experience_years,-rating` |
| Cheapest first | `consultation_rate` |

### Acceptance criteria
```
GET /api/lawyers/?search=soliyev               → only "Soliyev Jamshid"
GET /api/lawyers/?ordering=consultation_rate   → ascending by rate (200000 first)
GET /api/lawyers/?ordering=-experience_years   → 30y, 10y, 5y
GET /api/lawyers/?search=xxxxxx                 → count=0, results=[]
```

## 2. `GET /api/documents/templates/`

### Current behavior (reproduced)
```
GET /api/documents/templates/?search=sariq    → count=8 (full list, unfiltered)
GET /api/documents/templates/?ordering=price   → identical order to default
GET /api/documents/templates/?ordering=-price  → identical order to default
```

### Required behavior
- `?search=<text>` — `icontains` across template title + description.
- `?ordering=<fields>` — comma-separated multi-field ordering.

### Serializer fields available (for reference)
`id, slug, kind, title, description, document_language, price, currency,
category_slug, is_featured, rating, reviews_count, purchases_count`

### Implementation (DRF)
```python
from rest_framework import filters

class DocumentTemplateViewSet(...):
    filter_backends = [
        DjangoFilterBackend,          # keep — category/kind/is_featured/price
        filters.SearchFilter,         # ADD
        filters.OrderingFilter,       # ADD
    ]

    search_fields = ["title", "description"]

    ordering_fields = [
        "price",
        "purchases_count",
        "rating",
        "reviews_count",
        "id",
    ]
    ordering = ["-purchases_count", "-rating"]   # default
```

### Client contract — exact `ordering` values
| Sort option | `ordering=` value |
|---|---|
| Most popular (default) | `-purchases_count,-rating` |
| Top rated | `-rating,-reviews_count` |
| Price: low → high | `price` |
| Price: high → low | `-price` |
| Newest | `-id` |

### Acceptance criteria
```
GET /api/documents/templates/?search=sariq    → only "Sariq chiroq"
GET /api/documents/templates/?ordering=-price  → 30000, 25000, 25000, 20000, …
GET /api/documents/templates/?ordering=price   → 15000, 20000, …
```

## Notes / out of scope

- **`min_rate` on `/api/lawyers/` is accepted but ignored** (e.g.
  `min_rate=1000000` still returns the 200k/250k lawyers). The web's
  `LawyerQuery` sends it, so it's a pre-existing backend gap, not part of this
  request — flagged here for awareness. Decide whether `min_rate` should be a
  lower-bound on `consultation_rate`.
- Keep the existing param **names** unchanged (`search`, `ordering`,
  `specialization`, `region`, `category`, `kind`, `is_featured`,
  `min_*`/`max_*`). The clients are already wired to these.
- Search should be `icontains` (DRF default, no `^`/`=`/`@` prefix) so partial
  substrings match. If the dataset grows large, consider Postgres full-text
  (`@` search prefix) later — not required now.
- Both endpoints are public (no auth) and paginated `{count, results, next,
  previous}`. Search/ordering must apply **before** pagination (DRF does this
  automatically once the filter backends are added).
